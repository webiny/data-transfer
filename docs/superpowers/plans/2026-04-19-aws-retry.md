# AWS Retry + Error Classification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace three separate hardcoded retryable-error lists with one unified classifier, opt DDB + S3 SDK clients into `retryMode: "adaptive"`, wire opensearch-js `maxRetries` via a new `tuning.os.maxRetries` field, and make `OsCommandExecutor.withRetry` classifier-gated.

**Architecture:** `src/base/isRetryableAwsError.ts` becomes the single source of truth for "is this AWS error worth retrying?". DDB and S3 retry loops delegate to it, replacing their local `isRetryable` ternaries. The SDK's built-in `adaptive` retry strategy runs inside the client (enabled via `retryMode`) and handles rate-control + throttle backoff internally; our outer `executeWithRetry` catches whatever the SDK still surfaces (e.g., after SDK's own retry attempts exhaust) and retries based on the classifier. For OpenSearch, `@opensearch-project/opensearch` Client gets `maxRetries` config; `OsCommandExecutor.withRetry` (which wraps index-ensure orchestration) uses the classifier so non-throttle errors fail fast.

**Tech Stack:** TypeScript strict, vitest, `@webiny/aws-sdk` (DDB + S3), `@opensearch-project/opensearch`.

**Reference spec:** `docs/superpowers/specs/2026-04-19-aws-retry-design.md`.

- [ ] **Step 3: Create the classifier**

Create `src/base/isRetryableAwsError.ts`:

```typescript
const RETRYABLE_ERROR_NAMES = new Set<string>([
    // DynamoDB throttles
    "ProvisionedThroughputExceededException",
    "ThrottlingException",
    "RequestLimitExceeded",
    "TransactionCanceledException",

    // S3 throttles
    "SlowDown",
    "RequestTimeout",
    "RequestTimeTooSkewed",
    "ServiceUnavailable",

    // Account-wide / cross-service throttles
    "TooManyRequestsException",
    "LimitExceededException",
    "Throttling",

    // AWS internal
    "InternalFailure",
    "InternalServerError",
    "InternalError",

    // Node-level
    "ECONNRESET",
    "ETIMEDOUT",
    "EPIPE",
    "ENOTFOUND"
]);

const RETRYABLE_STATUS_CODES = new Set<number>([408, 425, 429, 500, 502, 503, 504]);

interface AwsErrorLike {
    name?: string;
    code?: string;
    $metadata?: { httpStatusCode?: number };
    $retryable?: { throttling?: boolean };
}

/**
 * Classifies whether an AWS SDK / network error is worth retrying.
 *
 * Covers: DynamoDB throttles, S3 throttles, account-wide API quotas,
 * transient AWS internal failures, HTTP 429/5xx, and node-level socket
 * errors. Everything else (auth, validation, bad-request, resource-not-
 * found) fails fast.
 */
export function isRetryableAwsError(error: unknown): boolean {
    if (!error || typeof error !== "object") {
        return false;
    }
    const candidate = error as AwsErrorLike;

    if (candidate.$retryable?.throttling === true) {
        return true;
    }

    const name = candidate.name ?? candidate.code;
    if (typeof name === "string" && RETRYABLE_ERROR_NAMES.has(name)) {
        return true;
    }

    const status = candidate.$metadata?.httpStatusCode;
    if (typeof status === "number" && RETRYABLE_STATUS_CODES.has(status)) {
        return true;
    }

    return false;
}
```

```typescript
private async withRetry<T>(fn: () => Promise<T>, label: string): Promise<T> {
    let lastError: Error | undefined;
    const schedule = this.retrySchedule;

    for (let attempt = 0; attempt <= schedule.length; attempt++) {
        try {
            return await fn();
        } catch (error) {
            lastError = error as Error;
            if (!isRetryableAwsError(error)) {
                throw error;
            }
            if (attempt < schedule.length) {
                const wait = schedule[attempt];
                this.logger.warn(
                    `${label} failed (attempt ${attempt + 1}/${schedule.length + 1}). Retrying in ${wait / 1000}s...`
                );
                await new Promise(resolve => setTimeout(resolve, wait));
            }
        }
    }

    throw lastError;
}
```

## Summary

- `src/base/isRetryableAwsError.ts` (new) — one classifier, 8 tests.
- DDB + S3 clients — `retryMode: "adaptive"` + classifier-driven outer retry.
- OpenSearch client — wired `maxRetries` from `tuning.os.maxRetries`.
- `OsCommandExecutor.withRetry` — classifier-gated. Non-throttle errors fail fast.
- Schema — added `tuning.os.maxRetries?: number`.
- Bootstrap — forwards `tuning.os.maxRetries` into the OS client config.

Behavior delta:
- **Retries get broader** on expected throttle / transient AWS errors (account-wide throttles, HTTP 5xx, node socket errors) across all three clients.
- **Retries get narrower** on OS bulk-path: a non-throttle error (bad mapping, auth, validation) fails fast instead of burning the 95-second retry schedule.
- **AWS SDK manages its own adaptive rate bucket internally** for DDB + S3 — no user-declared perSecond budget.
